# Матмодель генерации токена gemma-4 12B: KV-кэш и два режима мульти-GPU (PP vs TS)

Статус: этап 2 плана C-17/TS (трекер `docs/c17-ts-plan-tracker.md`). Все числа верифицированы
кодом (`inference_math.py`, тесты `tests/test_inference_math.py` — **25/25 зелёных**,
hand-values сверены в `tmp-src/verify_stage2.py`); механизм выведен пер-строчно из исходников
llama.cpp upstream master на commit **d327bf1f** (`src-llama-cpp-b11819/`, имя каталога — misnomer).

## 0. Что моделируется и обозначения

Модель описывает **decode одного токена в позиции S** (batch=1): прогон скрытого состояния
[3840] через 48 слоёв, запись/чтение KV-кэша на каждом слое, и два режима работы на двух
картах (N=2):

- **PP — layer split**: слои разбиты по картам блоками, каждая карта держит веса и KV своих слоёв;
- **TS — tensor parallelism**: матрицы каждого слоя разрезаны между картами, карты работают параллельно.

| Обозначение | Значение (gemma-4 12B) |
|---|---|
| `d_model` | 3840 |
| `L` | 48 слоёв: **40 SWA** + **8 global full** на индексах {5, 11, 17, 23, 29, 35, 41, 47} (шаг 6) |
| `n_q` / d_head | 16 query-head'ов; d_head = 256 (SWA) / 512 (global) |
| `q_dim` | SWA: 16·256 = **4096**; global: 16·512 = **8192** |
| `kv_heads` / kv_dim | SWA: 8 × 256 = **2048**; global: **1** × 512 = **512** |
| FFN | GeGLU (gate/up/down, GELU), ff_dim = 15360 → 3 матрицы на слой |
| RoPE | SWA base 1e4; global base 1e6 + пропорциональные `rope_freqs` [256] |
| lm_head | **tied** с token_embd [3840×262144]; final_logit_softcapping = 30.0 |
| контекст | context_length = 262,144; в dense-12B нет PLE и MoE |

Параметры (ground truth из tensor list GGUF v3, `tmp-src/tensors.txt`, 667 тензоров):

| Величина | Значение |
|---|---|
| Всего параметров (все тензоры) | **11,907,350,576** (= «11.91 B» из E1 ✓) |
| `P_gemm` — параметры GEMM-матриц слоёв | **10,899,947,520** = 40×224,133,120 + 8×241,827,840 (tied lm_head — без vocab·d по конвенции проекта) |
| `W` — байт VRAM-чтения весов на токен (Q4_K_M, 0.61776 B/параметр) | **P_gemm · 0.61776 = 6,733,551,579.9552 B** |

Ключевой архитектурный факт: у global-слоёв **нет тензора attn_v** (13 тензоров/слой против
14 в SWA) — `Vcur = Kcur` как alias сырой k-проекции (`src/models/gemma4.cpp`, строки 253–255:
«if v_proj is not present, use Kcur as Vcur»). Отсюда и механизм краша C-17 (раздел 5.3).

## 1. Цепка операций на токен в слое (source-grounded)

Пер-строчная цепка из `src/models/gemma4.cpp` (строки 201–397), одинаковая для обоих типов слоёв,
если не указано иное:

```
inpL [d_model]
 1. cur = RMS(attn_norm · inpL)                    # learned per-channel norm [3840]
    ── attention ──
 2. Qcur = mm(wq) → reshape [d_head, n_q=16]
       → RMS per-head (attn_q_norm, learned) → RoPE
 3. Kcur = mm(wk) → reshape [d_head, n_kv]
       → RMS per-head (attn_k_norm, LEARNED, [d_head]) → RoPE      # строки 252–270
 4. V:   SWA    — Vcur = mm(wv) → plain rms_norm (без весов)        # строка 264
         global — Vcur = Kcur-alias → plain rms_norm (без весов). RoPE на V нет.
 5. FA(Q,K,V) + mm(wo)                                 # build_attn, строки 273–278
       ── под TS: wo-mm даёт PARTIAL → allreduce №1 (раздел 5.1) ──
 6. cur = RMS(attn_post_norm · attn_out) + inpL      # learned norm [3840] + residual
    ── FFN (GeGLU, LLM_FFN_GELU | LLM_FFN_PAR) ──
 7. x = RMS(ffn_norm); out = mm(ffn_down)( GELU(mm(ffn_gate)x) · mm(ffn_up)x )
       ── под TS: ffn_down-mm PARTIAL → allreduce №2 ──
 8. cur = RMS(ffn_post_norm · out) + attn_out        # residual
inpL ← cur   (×48 слоёв; в dense-12B нет PLE/MoE/out_scale)

после слоя 47: output_norm → lm_head GEMM (tied таблица [3840×262144]) → softcap(30)
```

**KV-запись** на каждую новую позицию decode: каждый KV-слой дописывает строки K и V в свой
буфер — SWA: kv_dim = 2048, global: kv_dim = 512. Оба буфера пишутся даже там, где значения
происходят из одной проекции (global): K проходит learned qk-norm + RoPE, V — plain rms_norm,
и в кэше это **две отдельные строки** [kv_dim]. На это указывает и наклон фита E1: 16,384 B/pos
f16 = 8 слоёв × (K 512 + V 512) элементов × 2 байта — т.е. K и V хранятся независимо.

**KV-чтение** на decode-токен в позиции S: FA читает строки K/V позиций, видимых слою:
global — **все S**, SWA — `min(S, окно=1024)` (кольцевой буфер фиксированного размера).

## 2. Байт по шине на токен и как их растят контекст и слои

Формула чтения decode-токена в позиции S:

```
bytes/token(S) = W + Σ_l KV_read_l(S)
KV_read_l(S)   = full:  S · (2·kv_dim_l) · e          # линейно в S
                SWA :  min(S, W_win) · (2·kv_dim_l) · e   # насыщается на окне
```

где `e` — байт на элемент KV-кэша (f16 → 2, q8_0 → 1), `W_win = 1024`.

### 2.1 Рост контекста: ∂bytes/∂S

Линейно с S растут **только full-слои** — SWA-буфер после заполнения окна константа. Поэтому

```
∂bytes/∂S = kv_slope = e · Σ_full (2·kv_dim_l)
gemma-4:   f16 → 8 слоёв × 1024 elem × 2 B = 16,384 B на каждую новую позицию контекста
           q8  → 8,192 B/pos
```

**Каждый дописанный в контекст токен добавляет ровно 16,384 байта (f16) к чтению каждого
следующего decode-токена** — это и есть «рост контекста → рост данных по шине». Число
16,384 B/pos f16 совпадает с наклоном эмпирического фита E1 **×1.00 (R²=0.998)** — модель
воспроизводит замер без поправок.

Константный SWA-член при S ≥ окна:

```
c_swa = W_win · Σ_SWA (2·kv_dim_l) · e
gemma-4 f16 → 1024 × 40 × 4096 elem × 2 B = 335,544,320 B (≈320 MiB) — не зависит от S
```

### 2.2 Влияние числа и типа слоёв: per-layer таблица

| Слой | P_layer (GEMM) | W-байт/токен (Q4_K_M) | KV-чтение @S=131,072 f16 | ∂KV/∂S |
|---|---|---|---|---|
| SWA (40 шт., напр. il=0) | 224,133,120 = q 15,728,640 + k/v 2×7,864,320 + o 15,728,640 + FFN 176,947,200 | **138,460,476.21** | min(S,1024)·4096·2 = **8,388,608** (константа при S≥1024: @131k и @262k — одно значение) | 0 за окном |
| GLOBAL full (8 шт., напр. il=5) | 241,827,840 = q 31,457,280 + k 1,966,080 (**v нет — V=K**) + o 31,457,280 + FFN 176,947,200 | **149,391,566.44** | S·1024·2 = **268,435,456** | 1024 elem × e на слой |

Числа пересчитаны кодом (`layer_weight_bytes_per_token`, `layer_kv_read_bytes_per_token`)
и зафиксированы в тестах. Выводы:

- **global-слой «дороже» SWA** и по весам (+10,93 MB/токен), и по KV-чтению (S-зависимое):
  у него q_dim вдвое больше (8192 vs 4096) при вдвое меньшем kv_dim (512 vs 2048);
- **число full-слоёв задаёт наклон роста**: каждая пара K+V строк global-слоя добавляет
  2×512×e байт/позицию; были бы 16 full-слоёв вместо 8 — наклон удвоился бы до 32,768 B/pos f16;
- **число SWA-слоёв задаёт константу**, а не рост: c_swa ∝ окно × Σ_SWA kv_dim.

### 2.3 Сводные значения KV(S) и bytes/token (S ≥ 1024)

`KV(S) = c_swa + S·kv_slope`:

| S | f16 KV(S) | q8 KV(S) | f16 bytes/token (= W+KV) |
|---|---|---|---|
| 131,072 | **2,483,027,968** | 1,241,513,984 | 9,216,579,548 |
| 262,144 | **4,630,511,616** | 2,315,255,808 | 11,364,063,196 |

Пересечение S\*, где чтение KV догоняет чтение весов:

- **f16 KV / Q4_K_M weights**: S\* = W/наклон ≈ **411,600** (конвенция `kv_crossover_tokens`,
  bits_w=4.95; с нативным b=4.94208 → 410,982) — C-15 «≈412k» это тот же пересчёт по старому P;
  за пределами нативного
  контекста gemma-4 (262,144): в рабочем диапазоне веса доминируют, KV — вторичный, но линейно
  растущий член: с 131k до 262k он прибавляет +131,072 × 16,384 = **2,147,483,648 B** (≈2.15 GB)
  к чтению на токен;
- конвенция `report` (KV в нативном dtype весов): S\* = W/(kv_elems_full·e_w) = **1,330,560**.

## 3. Режим 1: layer split (PP) — механизм и формула

Механизм (llama.cpp `-sm row`/split): слои разложены по картам **блоками**, вместе с KV-кэшем
своих слоёв; при генерации токена карты работают последовательно — карта №2 начинает свой блок,
когда карта №1 передала скрытое состояние [d_model] через PCIe. При batch=1 цепь сериализована:

```
bytes/карта = (W + KV(S)) / N          # каждая половина читает свою долю весов и KV
PCIe-член  = d_model · e на границу    # с N=2 — одна граница: 3840 × 2 = 7,680 B/токен
```

Для gemma-4 сплит симметричен (24/24 слои; full-индексы {5,11,17,23} в первой половине,
{29,35,41,47} во второй — по 4 full и 20 SWA каждая), поэтому формула точна.

**Важно:** формула даёт только байт на карту, **не потолок TPS** — при batch=1 выигрыша нет:
замер C-18 показал decode без прироста (33.19 t/s @131k, 26.89 t/s @256k), а prefill выиграл
×1.627/×1.650 (там карты параллелит сам prefill-пакет).

Проверенные значения (N=2):

| S | KV f16 → bytes/карта | KV q8 → bytes/карта |
|---|---|---|
| 131,072 | **4,608,289,773.98** | 3,987,532,781.98 |
| 262,144 | **5,682,031,597.98** | 4,524,403,693.98 |

Рост по шине на карту: ∂/∂S = kv_slope/N — f16 → **8,192 B/pos/карта** (наклон делится
между картами вместе с KV).

## 4. Режим 2: tensor parallelism (TS) — механизм и формула

### 4.1 Сплит-состояния тензоров и allreduce

`get_tensor_config` (`src/llama-model.cpp`) под TS назначает каждому тензору split-state;
ggml-meta-бэкенд (`ggml/src/ggml-backend-meta.cpp`) строит сабграфы по устройствам:

| Тензор | Сплит-состояние (N=2) |
|---|---|
| GEMM-веса attn_q/k/v, wo, ffn_gate/up/down | **SPLIT_AXIS_1** — матрица разрезана на 2 шарда по head/строкам |
| веса norm'ов (attn_norm, qk-norm, post-norm) | **MIRRORED** — полная копия на каждой карте |
| KV-кэш cache_k/v_lN [kv_dim × kv_size] | **AXIS_0** — head-split: карта i держит головы с начала/конца диапазона |

Каждый PARTIAL-узел (результат разрезанного GEMM, ожидающий сведения) становится границей
сабграфа в `graph_compute` → один allreduce по PCIe; merge-оптимизация не применяется
(partial-ветки суммируются только через allreduce). В слое gemma-4 PARTIAL ровно два:
**wo-mm и ffn_down-mm → 2 allreduce/слой, 96 на токен**. Байт по PCIe:

```
ts_comm = L · 2 · d_model · e = 48 × 2 × 3840 × 2 = 737,280 B/токен (f16)
```

— вторичный член: ~0.74 MB против ~9 GB VRAM-чтений @131k f16.

### 4.2 Идеальный TS (head-split KV во всех слоях; работает при n_kv_heads ≥ N везде)

Каждая карта читает долю W/N и долю KV/S:

```
bytes/карта = (W + KV(S)) / N      — та же формула, что у PP
потолок     = N × BW_eff / (W + KV(S))   # карты читают параллельно → N× single-GPU
```

gemma-4 при BW_eff = 397.7 GB/s (калибровано по замерам E1/E3 v2 на двух RTX 5060 Ti):
**≈86.3 t/s @131k f16, ≈70.0 t/s @262k f16; q8: ≈99.7 / ≈87.9**. Но для gemma-4 этот режим
**не работает** — см. 4.3.

### 4.3 Краш C-17 в global-слоях: механизм пер-строчно (source)

Цепка срабатывания assert'а (`handle_per_row`, ggml-backend-meta.cpp):

1. `Kcur = mm(wk[SPLIT_AXIS_1], cur[MIRRORED])` → `handle_mul_mat` даёт выход **AXIS_0** [512, tokens] —
   split по единственному (оси 0) диапазону: каждая карта держит **половину вектора одного kv-head'а**;
2. `ggml_reshape_3d(Kcur, d_head=512, n_kv_heads=1, tokens)`: base_ne_in = 256; размер оси 0 (512)
   делится на base без остатка (512 % 256 == 0), а осей с запасом голов нет (n_kv_heads = 1 < N) →
   **split остаётся на AXIS_0**;
3. `build_norm(Kcur, attn_k_norm)` — per-head RMS по строкам [d_head] → `handle_per_row` требует
   `src_ss[0].axis != SPLIT_AXIS_0` (нормировать можно только полный вектор) → **GGML_ASSERT падает**.
   То же на plain `ggml_rms_norm(Vcur)` — V-alias той же Kcur.

Почему не падают остальные пути:

- **SWA-слои**: 8 kv-head'ов ≥ 2 устройств → при reshape split мигрирует с оси 0 на ось 1
  (каждая карта держит 4 целых head'а), per-row norm проходит внутри head'а — безопасно;
- **Q-путь** во всех слоях: 16 q-head'ов ≥ 2 → то же;
- **стандартные модели** (llama/qwen/mistral…): либо нет learned per-head qk-norm, либо
  n_kv_heads ≥ N — head-split KV работает. Это и есть ответ на «Ollama/LM Studio TP работает»:
  gemma-4 global-слой — единственный случай **«1 kv-head + per-row norm»**, детерминированно
  бьющий в assert (та же структурная проблема задокументирована в hexagon, commit 78a8ae14:
  «2 KV heads on 4 cores»).

### 4.4 Mirror-KV патч (дизайн этапа 4) и формула режима

Патч ~15–25 строк в `llama-model.cpp::get_tensor_config`: для слоёв gemma-4 с
`n_head_kv(il) < n_devices` — веса attn_k/attn_v (attn_v у gemma-4 отсутствует, патчится
только k) и KV-буферы cache_(k|v)_lN → **MIRRORED** (per-layer проверка через hparams;
по regex'у тип слоя не различить). Тогда Kcur/Vcur — MIRRORED-тензоры: qk-norm/rms(V)/RoPE
проходят без assert, FA имеет путь kv_mirrored (полное чтение на карте), Q/O/FFN остаются
head-split с теми же 2 allreduce/слой. Формула режима:

```
bytes/карта = W/N + min(S, W_win)·kv_elems_swa·e / N     # SWA-KV head-split (8 голов ≥ 2)
            + S · kv_elems_full · e                      # full-KV mirror — НЕ делится
gemma-4:      = W/2 + c_swa/2·(S≥окно) + S × 16,384 (f16)
```

**Идентичность (проверена тестом):** для S ≥ окна `mirror(S) == ideal(2S)` — single kv-head
эффективно **удваивает наклон роста байт по шине**: ∂/∂S в mirror-режиме = полный 16,384 B/pos
против 8,192 у идеального head-split. Эквивалентно: mirror-TS @131k f16 == PP/идеал @262k —
обе дают **5,682,031,597.98 B/карта**.

## 5. Рабочие примеры (все числа верифицированы кодом; BW_eff = 397.7 GB/s)

| Режим | S=131,072 f16 | S=131,072 q8 | S=262,144 f16 | S=262,144 q8 |
|---|---|---|---|---|
| PP / TS-идеал: bytes/карта | 4,608,289,773.98 | 3,987,532,781.98 | 5,682,031,597.98 | 4,524,403,693.98 |
| TS-идеал: потолок t/s (теорема N×SG) | **86.30** | 99.7 | **69.99** | 87.9 |
| **TS mirror-KV (патч): bytes/карта** | **5,682,031,597.98** | 4,524,403,693.98 | 7,829,515,245.98 | 5,598,145,517.98 |
| **TS mirror-KV: потолок t/s** | **≈70.0 (69.99)** | ≈87.9 | **≈50.8 (50.80)** | ≈71.0 |

Сравнение с замерами C-18 (PP, decode): 33.19 t/s @131k / 26.89 t/s @256k — TS mirror-KV
предсказывает **≈70.0 / ≈50.8 f16** т.е. ~×2.1/×1.9 против PP при том же контексте: выигрыш
даёт параллельное чтение двух карт (в PP цепь сериализована). Эмпирическая проверка — этап 4,
E3 v3 (`-sm tensor -ts 1,1`, S=131k/262k × KV {f16, q8_0}, r≥2; 262k r=1) после сборки
патченного раннера (блокер: MSVC отсутствует на этой машине — решение за пользователем).

**Prefill** (для полноты модели): FLOPs полного prefill S токенов = GEMM-часть + ядра внимания.
Точное значение @S=131,072: **5,196,755,473,793,024** FLOP (GEMM 2,857,355,842,682,880 +
full-внимание 8 слоёв O(S²): 2,251,782,633,816,064 + SWA-внимание 40 слоёв O(S·окно):
87,616,997,294,080). Замер C-18: prefill PP ×1.627/×1.650 против single-GPU — параллельная
работа карт на батче токенов.

**FLOPs decode-шага**: 2·P_gemm = **21,799,895,040 FLOP/токен**; AI decode при S=0 ≈ 3.2 FLOP/B
(Q4_K_M) — глубоко memory-bound для любой GPU (ridge ≫), поэтому потолок TPS задаётся именно
байтами из разделов 2–4, а не вычислительной мощностью.
