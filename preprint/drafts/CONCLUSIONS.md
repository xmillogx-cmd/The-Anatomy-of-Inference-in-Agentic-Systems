# AoI — журнал выводов (C-xx)

Правило: вывод фиксируется только после пройденного теста/замера. Доказательство = тест в `tests/test_inference_math.py` или строка CLI `python inference_math.py report`. Все числа ниже воспроизводятся этим запуском.

## C-01 — Закон AI decode (2026-10-22)
При S=0 и нативном dtype  `AI_decode ≡ 16 / dtype_bits`: BF16/F16 → 1.0 FLOP/байт, F32 → 0.5.
Доказательство: `test_decode_ai_law` (все 9 моделей, rel<1e-6).

## C-02 — Decode всегда memory-bound (2026-10-22)
AI(S=0) ниже ridge любой из трёх GPU минимум в 82 раза (RTX-4090: ridge 82), у A100-80G ≥153×, у H100-SXM ≥295×; F32-модель (smollm) — ещё дальше (AI=0.5).
Доказательство: `test_decode_memory_bound_all_gpus` + столбец margin@4090 в report (82–164×).

## C-03 — Точные значения KV-кэша (2026-10-22)
Формула `KV = 2·L·kv_dim·S·e`: qwen2.5-3b @4k FP16 = **150,994,944 B** (ровно 144 MiB); tinyllama-1.1b @8k FP16 = **184,549,376 B**; qwen2.5-0.5b @32k FP8 = **201,326,592 B**.
Доказательство: `test_kv_exact_values` (равенство без допуска).

## C-04 — Параметры из header'ов = размер файла ≤1% (2026-10-22)
Считанные параметры × dtype совпадают с размером safetensors-файлов всех 7 текстовых фикстур в пределах 1% (у qwen2.5-3b/qwen3-4b — <0.01%; pythia-2.8b сходится после вычета U8 bias-буферов).
Доказательство: `test_param_count_vs_file_size`.

## C-05 — Потолки TPS и линейность квантования (2026-10-22)
Идеальный потолок (BW/байт на токен, batch=1): qwen2.5-0.5b @1008 GB/s: **≈1408.5 tok/s** native (BF16), **≈5634.0 tok/s** INT4 — ровно ×4 при 16→4 bit (линейность в memory-bound режиме). Полная таблица по 9 моделям × 3 GPU — в report (столбец «TPS nat» = нативный dtype файла; значения у tied-моделей пересчитаны после C-09).

## C-06 — KV-crossover S\* (2026-10-22)
Длина контекста, где чтение KV = чтению весов: qwen3-4b **S\* ≈ 49,280**, qwen2.5-0.5b **≈ 58,240** (fp16/fp16; после поправки tied-lm_head C-09 — W меньше). Выше S\* квантование KV даёт больший эффект, чем весовое; у GQA-моделей с малым kv_dim S\* ниже.
Доказательство: `test_kv_crossover_hand_values` + столбец S* в report.

## C-07 — Prefill compute-bound (2026-10-22)
AI prefill растёт с длиной промпта: qwen2.5-0.5b, T=4096 → AI ≈ 3827 FLOP/байт ≫ ridge RTX-4090 (82), при этом AI < T.
Доказательство: `test_ai_prefill_compute_bound`.

## C-08 — U8 в pythia-2.8b = каузальный bias, не квантизация (2026-10-22)
Тензоры `attention.bias [1,1,2048,2048]` uint8 на каждом из 32 слоёв (GPT-NeoX naming) — константные маски внимания, 32×4,194,304 B ≈ 127.5 MiB; они объясняют расхождение «параметры × dtype» и размер файла без квантизации весов.
Доказательство: дамп `tools/parse_headers.py names pythia-2.8b` + `test_param_count_vs_file_size` (вычет зашит в REFERENCE_MODELS).

## C-09 — Tied lm_head: decode читает одну строку, не таблицу (2026-10-22)
Когда lm_head делит таблицу с token_embd (`tied=true`), один токен decode читает из таблицы одну строку O(d_model), а не всю таблицу vocab·d. Старая формула завышала объём чтения весов: qwen2.5-0.5b — параметры GEMM 493,961,216 → **357,826,560** (фантом +38%); gemma-4-12B-it — фантом ≈1,006,632,960 параметров на каждый токен (vocab 262,144 × d_model 3840). TPS/crossover всех tied-моделей пересчитаны (C-05, C-06).
Доказательство: `test_gemm_params_hand_values` + tensor list GGUF v3 gemma-4 (тензор output.weight отсутствует — таблица одна, shared с token_embd).

## C-10 — Gemma-4: гетерогенное внимание (локальное SWA + глобальное full) меняет KV-математику (2026-10-22, исправлено 2026-10-23)
Gemma-4-12B-it: 48 слоёв = **40 локальных скользящих** (sliding_window=1024, kv_heads=8, per-head dim 256 → kv_dim=2048; `blk.0.attn_k [3840x2048]`) + **8 глобальных full-внимания** blk.5/11/…/47 (kv_heads=1, per-head dim 512 → kv_dim=512; `blk.5.attn_k [3840x512]`). Линейно в S растёт только глобальная часть: s_grow = 8×2×512 = **8,192 элементов/токен** (f16: 16,384 B/позицию); SWA-буфер ограничен min(S,1024) — константа c_swa = 40×2×2048×min(S,1024). Значения: f16 @S=32k = **872,415,232 B** (≈832 MiB); kv@8bit (e=1) @32k = **436,207,616 B**; S\* при w=4.95 bit / kv=f16 ≈ **412,236 токенов** — выше context_length модели (262,144).
Первичная формулировка («40 full + 8 SWA») была инвертирована: shapes тензоров были прочитаны верно, но ярлыки типов внимания перепутаны местами. Исправлено после сверки metadata GGUF v3 (sliding_window_pattern ↔ kv_heads; key_length=512 — глобальные головы) и подтверждения замером E1 (C-11).
Доказательство: `test_gemma_hetero_arch_values` (11/11 зелёные, 2026-10-23) + tensor list GGUF v3 gemma-4 (`blk.0.attn_k [3840x2048]`, `blk.5.attn_k [3840x512]`) + metadata (sliding_window_pattern, key_length/key_length_swa).

## C-11 — Замер E1 подтверждает гибридную архитектуру Gemma-4 (2026-10-23)

Доказательство: `experiments/E1-kv-correlation/` (raw/, table.md, plot.png, conclusion.md) + `test_gemma_hetero_arch_values`.

## C-12 — Квантование KV = чистый минус в decode TPS при S ≤ 32k (2026-10-23)

На этой конфигурации (b11819, RTX 5060 Ti) квантование KV не даёт выигрыша decode TPS в диапазоне S ≤ 32k; механизм overhead неизвестен — открытый вопрос (варианты: принять как измеренный факт / другой билд llama.cpp / исходники ggml-cuda).

Доказательства: (a) префлайт-смоук TS≈PP в пределах ≤0.4% (pp512 2261.15 vs 2269.64; tg32 50.70 vs 50.54); (b) все строки E3 на CUDA1 в пределах ≤0.6% от single-GPU baseline E2 на той же карте (pp@65k 1439.81 vs 1435.59; tg@131k 38.34 vs 38.09); (c) истинный TS вдвое сокращает чтение весов на токен → decode ~×2, наблюдаемо ×1.00–1.01; (d) строки PP имеют независимые std (±22.16 vs ±0.34) = отдельные запуски. Данные E3 v1 валидны только как per-card сравнение: две RTX 5060 Ti эквивалентны в пределах ~±3% на всех S. ## C-17 — Tensor split (`-sm tensor`) детерминированно крашится при построении графа на gemma-4 (2026-10-23)

Доказательство: `experiments/E3-multi-gpu-tp-ts/raw/preflight_ts_smoke.txt` (assert в хвосте) + ABORT-записи в run_log.txt (4 прогона).

## C-20 — Расчётная модель шины TS/PP: байты на карту одинаковы; TS на gemma-4 неизмерим в llama.cpp (2026-10-24)
Теоретическое закрытие TZ блока 6 (TS+PP, длинные S, разное квантование KV). Модель (`inference_math.py`): при любом сплите каждая карта читает на токен **P_gemm·b/8/N весов + KV(S)/N** — PP делит слои вместе с их KV; TS делит матрицы, и KV-кэш в текущем llama.cpp тоже распределён по устройствам: meta-callback `pattern_kv_cache ("cache_(k|v)_l\d*") → GGML_BACKEND_SPLIT_AXIS_0`, форма K/V-тензора `[n_embd_k_gqa, kv_size]` (llama-kv-cache.cpp) — ось 0 = пространство kv-head'ов; веса split_state режет на ненулевые contiguous-чанки на каждое устройство для каждого тензора (llama-model.cpp). Проверено по upstream master 24.10.2026 (web_fetch исходников); у gemma-4 слойный сплит симметричен (24/24, по 4 full-слоя в каждой половине) ⇒ формула точна.

Байты шины на карту (gemma-4 Q4_K_M, N=2), B/токен:
| S | KV f16 | KV q8_0 |
|---|--------|---------|
| 131k | **4,613,148,036** | **3,992,391,044** |
| 256k | **5,686,889,860** | **4,529,261,956** |

W = P_gemm·b/8 = 10,915,676,160 × 0.61776 = 6,743,268,104.6 B; KV f16 @131k = (131_072·8192 + 1024·163_840)·2 = 2,483,027,968 B (@256k: 4,630,511,616); q8_0 — вдвое меньше.

**Ревизия 2026-11-11 (этап 3 плана C-17/TS):** P_gemm поправлен **10,915,676,160 → 10,899,947,520**
(−15,728,640; −0.14%) — старое значение предполагало attn_v в global-слоях; по ground truth tensor list
GGUF v3 + `src/models/gemma4.cpp` у gemma-4 **V = K**, attn_v отсутствует, P_layer(global) = 241,827,840.
Новый W = 6,733,551,579.96 B (ΔW = −9,716,524.6). Таблица выше перевычислена на тех же KV-членах:
| S | KV f16 | KV q8_0 |
|---|--------|---------|
| 131k | **4,608,289,774** (было 4,613,148,036) | **3,987,532,782** (было 3,992,391,044) |
| 256k | **5,682,031,598** (было 5,686,889,860) | **4,524,403,694** (было 4,529,261,956) |

86.2/99.6 → **86.3/99.7** t/s @131k и 69.9/87.8 → **70.0/87.9** @256k (f16/q8_0, BW_eff=397.7).
Сопутствующая ревизия: S\* f16-KV ≈412k (C-15/C-19) → **≈411.6k** (`kv_crossover_tokens`, bits_w=4.95).
Выводы C-20 не меняются (равенство байт PP/TS-идеала; allreduce 737,280 B/токен; краш TS — C-17).
Полная матмодель + механизм: `docs/mode-math-model.md`.

Главный вывод: **PP и TS дают одинаковые идеальные байты шины на карту; разница режимов временна.** PP при batch=1 сериализует половины токена ⇒ выигрыша decode TPS нет (C-18). TS параллелит чтения тех же объёмов — идеальный потолок = N × SG-потолок: 86.2/99.6 t/s @131k, 69.9/87.8 @256k (f16/q8_0, BW_eff=397.7 GB/s по фиту E1+E2) минус overhead allreduce — L·2·d_model·e = 48·2·3840·2 = **737,280 B/токен** по PCIe (вторичный член: ~0.7% от чтений @131k f16; P2P между двумя RTX 5060 Ti нет — через host-память). Замеренный PP tg: 33.19/25.58 @131k, 26.89/18.03 @262k — ниже идеала из-за dequant/kernel-overhead (как и SG: 43.10 ideal vs 38.09 measured f16 @131k). Квантование KV вдвое режет KV-член, но dequant делает его чистым минусом в обоих режимах: идеальное q8_0/f16 = **1.156@131k / 1.256@256k** против замеренных 0.748/0.634 (SG, C-15) и 0.771/0.671 (PP, C-19).

Эмпирические данные TS на этой модели/стеке невозможны: механизм краша C-17 переверифицирован по upstream master — `handle_per_row` в ggml-backend-meta.cpp ассертит `src_ss[0].axis != GGML_BACKEND_SPLIT_AXIS_0` для per-row ops (k-norm/hybrid SWA gemma-4 попадает детерминированно); дополнительно у глобальных слоёв n_embd_k_gqa = 512 (один kv-head) — contiguous axis-0 сплит на N=2 даёт каждой карте полголовы (структурный блок).
